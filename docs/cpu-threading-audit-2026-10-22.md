# CPU threading audit: JobSystem use, serial hot spots, prefetch candidates (Thema 238, Schritt 1)

22.10.2026, MacBook Air M5 (10 cores, 24 GB), **Metal only**. Inventory and measurement, **no engine code changed** (new: `scripts/perf/thread_timeline_report.py`,
`scripts/perf/make_land_game_dir.py`, raw data in `perf-audit/raw-cpu-threading/`). D3D11/D3D12/Vulkan/OpenGL were not run; where a finding names their code it is read, not measured.

## 1. Verdict

1. **During play the pool is almost idle and the main thread is not.** Per pool thread 0.5 to 2 % busy (10k entities: 0.5 %, 100k world with cells: 1.8 %, landscape + foliage: 0.7 %, and nothing at all in the editor's steady state). The main thread's own work is 2.6 to 7.8 ms per frame; the rest of the frame is `Metal::NextDrawable`.
2. **What is parallel today is small:** `FrustumCull` and `ExtractMeshes` chunks (10k entities: 1.5 ms CPU per frame spread over 10 lanes), `SkyEnvBake` (all 10 lanes once, 40 to 64 ms), `CellLoad`/`CellJsonRelease`, `SceneParse`. Every other hot item below runs on the main thread.
3. **Biggest serial items** (shares are of main-thread work per frame): `ExtractFoliage` 22 to 38 %, the extract gather + transform propagate + bounds refine ~40 % at 10k entities, then one-time spikes: foliage scatter 124 to 142 ms, `SkyNoise3D` 1.6 CPU-s at start, first-draw asset loads 140 to 220 ms each in the editor.
4. The two named candidates in the brief are **not** the big ones: the GI landscape table (`RenderExtractor.cpp:349`) costs ~0.06 ms (standalone micro-bench of the 5x16x16 sRGB decode, 0.064 ms per call, not scoped in the engine); the two `parallel_for` sites (`:453`, `:563`) are not the problem, the serial gather in front of them is.

## 2. How it was measured (timeline = profiler v3 per-thread lanes, cross-checked with a per-thread CPU probe)

* Driver: `he_perf_capture.py` (editor) or `HE_PROFILE_CAPTURE` on `HorizonGame` (hidden window), `--no-counters`, vsync off, then `thread_timeline_report.py` on the dump: lane busy (union of depth-0 spans), main-thread WAIT (`WaitForFrame`/`NextDrawable`) vs WORK, pool occupancy in 1 ms bins, hitch frames. **Profiler numbers.** Pool stats (`ThreadPoolStats`) are not in the dump and no API call reaches them from outside; the cross-check is `scripts/perf/thread_cpu_probe.c` (`DYLD_INSERT_LIBRARIES`, Mach `thread_info`): in the cells run the 10 pool threads show 152 to 179 ms CPU each against 174 to 214 ms span wall time in the profiler, so no un-scoped pool work is hiding. **No xctrace was used.**
* Binaries: editor + `HorizonGame` of worktree `claude-auto-landscape-material-2-0-alle-` (HEAD `6479c3d1`; this branch differs only in `Window.cpp`/`EditorApplication` window placement, checked with `git diff --stat`). One run repeated on this branch's own build (`own-steady-s512x4`: work p50 2.88 vs 3.18 ms, same shape). `he_tests` and `HorizonEditor` of this branch built (rc 0, 1856 steps).
* Scenes: `/tmp/al2/scenes/s512_x4.hescene` (512 m auto landscape, 5 foliage layer meshes, 425k stored / 9k in range), `s128_x16` (102k stored), reference world 10k meshes (extent 400), reference world 100k split in 256 cells (`split_scene_cells.py`, load 1100 m). Game dirs via `make_land_game_dir.py` (adds a camera). Camera static in all runs.
* Conditions (honest): **screen locked** (`CGSSessionScreenIsLocked=Yes`), so `Metal::NextDrawable` blocks 20 to 40 ms and the WAIT share is inflated; the WORK numbers are CPU time and unaffected. AC power, low-power off, thermal nominal, load 2 to 5 before the runs. **A second bee (topic 237) ran editor captures on the machine in parallel** during parts of this session (the ref10k first run, the build period); runs were started only when no other Horizon process was visible, but the ref10k p99 (48 ms hitches) is probably theirs. Single runs, no noise floor measured except: warm editor load (3 runs) and steady (2 runs, 3.18 / 2.88 ms).

## Handoff

- **Topic / step:** Thema 238, Schritt 1 (inventory + measurement). Branch `claude/cpu-threading-audit-jobsystem-auslastung-daten-vorbereitung-`; documentation and two measurement scripts only.
- **Verified:** section 3 numbers from dumps in `perf-audit/raw-cpu-threading/*.report.txt` (all Metal); pool-lane busy vs probe CPU (cells run, `threads-cells100k.tsv`); `extractFoliage` has no `parallel_for` (read `FoliageExtract.cpp:399-640`); `he_tests` builds; `test_async_streaming` passes; `test_hpak` 58/59 with the known `scanContentDirectory` failure (`6 == 2`), **passes 59/59 with `HOME=/tmp/cta/emptyhome`**.
- **Not verified:** D3D11/D3D12/Vulkan/OpenGL (no measurement; code sites listed only), real GPU-unlocked frame times (screen was locked), async asset path under a landscape (no pak/engine content in the game dir; item 7), sky rebake during day/night, moving camera (all runs static), exported game, noise floor of the single runs, Linux/Windows.
- **Decisions taken:** measured on the neighbour worktree's binaries (diff = window placement only); did not touch the ThreadPool API or Jolt; profiler lanes + DYLD probe instead of xctrace.
- **Decisions suggested, not taken:** order for step 2: (1) `extractFoliage` memo + parallel buckets, (2) scatter per layer on the pool, (3) pre-resolved bounds table for the extract gather, (4) SkyNoise3D cache, (5) add profiler scopes to `parseAndRegisterAsset`, sky rebake and `warmupWorldMaterials` before changing them.
- **Traps:** a locked screen turns `NextDrawable` into 20 to 40 ms waits (the game dump has no `WaitForFrame`, the report subtracts `NextDrawable`); the dump holds only pool tasks that open a scope, so name every `post/schedule`; `timeout` does not exist on macOS (use a kill loop); the other bee's editor runs overlap yours, check `pgrep HorizonEditor` before each run.
