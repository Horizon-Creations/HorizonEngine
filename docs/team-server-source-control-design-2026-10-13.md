What the feature is: per project, a team may switch from "everyone talks to git directly"
to "everyone saves through the team server". The server merges the saves of all members,
settles conflicts by a fixed rule and keeps a record of every decision. In the background
it pushes its state to a GitHub repo the team picks. The direct git integration
(`HE_SourceControl`, `SourceControlPanel`) stays and remains the default.

## 1. Decisions at a glance

| Question | Decision | Section |
|---|---|---|
| Where does the team's state live? | One **bare git repo per team project** on the server, written only by the server through git plumbing | 3 |
| Who merges? | The **server**, one upload at a time per project, in arrival order | 5 |
| Merge unit | **Per file**, with the file's own base (what the editor last got from the server) | 5.1 |
| Scenes (`.hescene`) | **Structural 3-way merge keyed by entity `uuid`** (server parses JSON) | 5.3 |
| Other JSON (`Config/*.json`, `.heproj`) | Structural 3-way merge by object key, arrays atomic | 5.3 |
| Plain text (scripts, shaders, docs) | `git merge-file`; conflicting hunks: **later arrival wins**, insert/insert keeps both | 5.4 |
| Graph formats + binaries (`.hmat .hmatfn .hcode .hpart .hasm .huiw`, `.hasset`, media) | Whole file: **later arrival wins** | 5.5 |
| What a loser keeps | Losing content goes to branch `horizon-conflicts` (never as sibling files in the project) and is named in the commit | 5.6 |
| Transport | A separate **sync connection** on port 7777 that authenticates with a ticket from the team connection; frame types 10-13 | 4 |
| Backup | `git push` of `main` + `horizon-conflicts` to the team's GitHub repo, **SSH deploy key** generated by the server, debounced after each change | 7 |
| Opt-in | `Config/ProjectSettings.json` → `sourceControl.mode = "teamServer"` (default `"git"`) + server-side project created by a team admin | 6.1 |
| Encryption of the team/sync connection | **Open, the human decides** (question posted to topic 199 for the queen). Blocks deployment to the internet host, not steps 2-4 | 8 |

## 2. What does not change

* Direct git stays: a project with `mode = "git"` (every project today) behaves exactly as now.
* Live collab sessions stay as they are. The existing rule "inside a session only the host
  syncs with source control" (enforced in `GitController::mayModify()`,
  `src/HE_Editor/GitController.h:52`) applies to team sync too: session clients pause their sync and the host saves for all.
* No per-role rights (out of scope). The only rights check is topic 197's admin flag, used
  for project creation and backup configuration.
* No locking. The merge rules replace it, as the live session does for the multi-user moment.

## 3. Server storage model

```
<data-dir>/teams.txt                          topic 197, untouched
<data-dir>/sc/<fold(team)>/<project>/
    repo.git/                                 bare repo, branch main + horizon-conflicts
    repo.git/lfs/objects/aa/bb/<sha256>       content of large media (git-lfs layout)
    index.txt                                 head manifest: path, sha256, git oid, size, mode
    project.txt   (0600)                      created, creator, backup url, backup state
    backup_key, backup_key.pub (0600)         ssh deploy key for the backup
    known_hosts                               pinned github.com host keys
```

* One linear history on `main`: **one commit per accepted upload**, author = the member
  (`<member> <member@<team>.horizon-team>`), committer = `Horizon Team Server`. Revision
  numbers are the commit count (`rev`), monotonically increasing; the oid is also sent.
* The server writes with plumbing only: `hash-object -w --no-filters`, a temporary
  `GIT_INDEX_FILE` + `update-index --cacheinfo`, `write-tree`, `commit-tree`,
  `update-ref refs/heads/main <new> <old>` (compare-and-swap). `cat-file --batch` reads.
  No working tree, no `git merge`, no `merge-tree --write-tree` (needs git ≥ 2.38; the
  host's version is unknown). Bytes are stored as uploaded (no eol filter on the server;
  the project's `* text=auto eol=lf` is the editor's business).
* Large media (`RepoConfig::isAutoLfsCandidate`, ≥ `kAutoLfsThresholdBytes` = 50 MiB) is
  stored as an **LFS pointer** in the tree plus the object under `lfs/objects/`, and the
  server appends the `filter=lfs` line for that exact path to `.gitattributes` in the same
  commit (as `GitService`'s CommitAll pre-pass does locally). Clients never see pointers:
  they fetch content by sha256. Non-media ≥ `kHardLimitBytes` (100 MiB) is refused at upload
  with its name, the same rule as the direct git path.
* Why git and not an own blob store: the backup becomes a plain push, LFS comes with it, and
  every revision is inspectable with standard tools on the host. The cost is a `git`
  (+ `git-lfs`, `openssh-client`) dependency on the server host, a deploy change (section 9).
* All git work and all merges run on **one worker thread per server** (a queue of jobs,
  one project at a time is enough at team scale). Results come back to the event loop
  through a self-pipe registered with `Poller`. The event loop never forks or merges; it
  already stalls ~25 ms per login for PBKDF2 and must not stall for a scene merge.

## 4. Protocol

Same port, framing and `"HERL" | 1 | type` header as the relay and topic 197.
Numbers taken: types 1-8 (relay + 197), **9 = TEAM_EVENT** (197 step 9, in progress).
This feature reserves **types 10-15** and status codes **5, 27-29** (posted to topic 197).

### 4.1 Why a second connection

The team connection caps a frame at `kMaxTeamPayload` = 1024 bytes and closes on anything
else (`HandleTeamRead`). Raising the cap there would put megabyte transfers in front of
presence events on the same TCP stream. So a sync runs on its own connection:

1. On the logged-in team connection: `TEAM_REQUEST op SC_TICKET` (op number = first free
   after 197 step 9) with `project str8`. Reply body: `ticket 16 bytes`, valid 60 s, single
   use, bound to (team, member, project). No password is resent and no hash runs.
2. New TCP connection, first frame `SC_HELLO (10): team str8 | member str8 | project str8 |
   ticket 16 bytes`. Answer STATUS `sc-ready` (5), or `bad-login` (23, ticket unknown,
   expired or used), `no-project` (27), `bad-hello` (16), `bad-version` (17), then close.
3. Removing a member (`DropMember`) also closes its sync connections and drops its tickets.
4. The sync connection **stays open** across saves for as long as the editor has the project
   open (TCP keepalive as for team connections). A new ticket is only needed after it drops.

### 4.2 Frames after `sc-ready`

```
SC_REQUEST (11): request u32 | op u8 | fields …          client -> server, ≤ 64 KiB
SC_REPLY   (12): request u32 | result u8 | text str16 | body …   server -> client, ≤ 64 KiB
SC_DATA    (13): request u32 | offset u64 | last u8 | bytes (≤ 1 MiB)   both directions
```

`str16` = u16 BE length + bytes. Paths are UTF-8, `/`-separated, project-relative, no `..`,
no leading `/`, ≤ 1024 bytes. Lists that can be long (manifests, commit entries) travel as an
SC_DATA stream of the same request, in the line format given per op, then the SC_REPLY.

| op | Name | Request fields | Reply / stream |
|---|---|---|---|
| 1 | HEAD | – | `rev u64`, `oid str8` |
| 2 | MANIFEST | `rev u64` (0 = head) | stream: `path \t sha256hex \t size \t mode \n` |
| 3 | HAVE | stream: sha256hex per line | stream: the ones the server does **not** have |
| 4 | GET | `sha256 32 bytes` | stream: content (also LFS content and preserved losers) |
| 5 | PUT | `sha256 32`, `size u64` | client streams content; server verifies the hash, stages it |
| 6 | COMMIT | `base_rev u64`, `message str16`; stream of entries | `rev u64`; stream of outcomes (5.6) |
| 7 | LOG | `from_rev u64`, `count u16` | stream: rev, member, time, message, outcomes |
| 8 | CREATE_PROJECT | – (admin) | – |
| 9 | BACKUP_SET | `url str16`, `branch str8` (admin) | `pubkey str16` (the deploy key) |
| 10 | BACKUP_STATUS | – | `pushed_rev u64`, `state u8`, `last_error str16`, `time u64` |

COMMIT entry line: `op \t path \t base_sha256|- \t new_sha256|- \n` with op `A` add, `M`
modify, `D` delete. The `base` is the per-file base the editor holds (section 6.3); `base_rev`
is informative (it goes into the log and the trailer), the merge goes by per-file bases.

Results: 0 ok, 1 bad-request, 2 not-admin, 3 missing-blob (COMMIT names a sha256 that was
never PUT), 4 too-large, 5 case-clash (a new path that equals an existing one up to case:
macOS and Windows checkouts would collide), 6 bad-path, 7 busy (queue full, retry),
8 backup-not-set, 9 server-error. A rejected request keeps the connection open.

### 4.3 Notifications

When `main` moves, every logged-in team connection of that team gets a `TEAM_EVENT` (type 9)
of a new kind `sc-head` with `project str8 | rev u64 | member str8`. That is 197 step 9's
mechanism; this feature only adds the event kind.

## 5. Merge and conflict resolution

### 5.1 Per-file algorithm (server, one COMMIT at a time per project)

For each entry with base `b`, uploaded `n` and current head content `h`:

| Case | Result | Outcome code |
|---|---|---|
| `h == b` | take `n` | `applied` |
| `h == n` | nothing to do | `same` |
| delete, `h != b` | keep `h`; the deletion is dropped (somebody changed it since) | `delete-dropped` |
| modify, path deleted at head | take `n` (a change beats a deletion) | `restored` |
| add, path exists at head (add/add) | scene/json: 3-way with an empty base (uuid/key union, 5.3); text and whole: 5.5 (a line merge with an empty base would glue two files into one) | `merged` / `merged-arrival` / `replaced` |
| otherwise | 3-way merge of (`b`, `h`, `n`) by file class (5.2) | `merged` / `merged-arrival` / `replaced` |

The whole COMMIT becomes **one** new revision. The reply lists every entry's outcome and the
resulting sha256, so the editor knows which files to fetch back (any whose result ≠ `n`)
plus all files others changed since the editor's last known revision.

"Later arrival wins" is the tie-break everywhere: the upload that reaches the server second
is the later save. It is deterministic (the server serialises per project) and easy to
explain to a user: *your save won where you both changed the same thing; the other version
is kept here*.

### 5.2 File classes

Decided by the project's `.gitattributes` first (`merge=binary` forces whole-file), then by
extension:

| Class | Extensions | Merge |
|---|---|---|
| scene | `.hescene` | 5.3 structural, entity-keyed |
| json | `.json`, `.heproj` and other files whose content parses as a JSON object | 5.3 structural, generic |
| text | `.lua .py .cpp .h .hpp .c .glsl .hlsl .metal .md .txt .ini .cfg .csv` | 5.4 line merge |
| whole | graph formats (`*.hmat *.hmatfn *.hcode *.hpart *.hasm *.huiw`, `merge=binary` today because their node ids are allocator-assigned), `.hasset`, images, audio, meshes, everything unknown or binary | 5.5 |

### 5.3 Structural JSON merge

A scene is `{ "version", "entities": [ … ], "levelScript"?, "cells"?, "streaming"? }`
(`SceneSerializer.cpp` `buildSceneJson`, ~line 1023). Each entity record has `uuid`, `name`,
`locked`?, `parent` (uuid or null), `children` (uuid list) and `components` (object keyed by
component name). Entity identity is the uuid, never the entt handle (that comment in the
serializer is exactly the merge argument).

* Entities are a map uuid → record. Added on one side only: kept. Deleted on one side and
  unchanged on the other: deleted. Deleted on one side and changed on the other: kept
  (`restored`, like 5.1).
* Inside a record: `name`, `locked`, `parent` are 3-way per field. `children` is a 3-way
  **list merge**: removals from either side apply, additions from both sides are kept
  (head order, then the arrival's new ones in its order). `components`: 3-way per component
  key; inside a component 3-way per field, recursing into objects; arrays and scalars are
  atomic values. A field changed differently on both sides: arrival's value, recorded.
* Top-level keys other than `entities`: 3-way per key, values atomic.
* Repair after the merge, each recorded: a `parent` naming a missing entity becomes null
  (root); `children` entries naming missing entities are dropped; `parent`/`children` that
  disagree are rebuilt from `parent` (one field wins so the hierarchy can't split); a cycle
  drops the edge that the arrival introduced.
* Output order: head's entity order, new entities appended in the arrival's order. Written
  as `dump(4)` with the **same nlohmann version the engine uses (v3.11.3,
  `CMakeLists.txt` FetchContent)**, so key order (sorted) and number formatting match what
  the editor writes. Untouched files are stored byte-for-byte and never re-dumped.
* Generic JSON (settings): the same object recursion without the entity map.
* The server needs a JSON parser: vendor `nlohmann/json.hpp` (single header, MIT) into
  CollabSession under `third_party/`. That relaxes the repo's "no external dependencies"
  line from "nothing at all" to "nothing to install"; the alternative, a server-side helper
  built from engine sources, would tie the server's deploy to an engine build.
* A merged scene that fails to parse back (it should not) falls back to 5.5 and is recorded.

### 5.4 Line merge

Temporary files for base/head/arrival, `git merge-file -p --diff3`, then the server walks
the conflict blocks itself: a block whose base part is empty (both sides inserted at the same
place) keeps **both** (head's lines, then the arrival's); any other block takes the arrival's
side. Outcome `merged` when there was no block, `merged-arrival` with the block count
otherwise.

### 5.5 Whole file

The arrival's file replaces head's, outcome `replaced`. Head's version is preserved (5.6).
For graph formats this is a stopgap; once their node ids are stable (as scene entity ids
already are), they move to a structural merge like 5.3.

### 5.6 Traceability and preserved losers

* Every revision's commit message ends in trailers, one per file:
  ```
  Save by alex (rev 42, base rev 40)

  Horizon-Revision: 42
  Horizon-Member: alex
  Horizon-Merge: applied Scripts/door.lua
  Horizon-Merge: merged-arrival Scenes/Main.hescene against r41 by connor (2 fields) lost=horizon-conflicts:r42/Scenes/Main.hescene
  Horizon-Merge: delete-dropped Content/Old.hasset changed in r41 by connor
  ```
* Whenever head-side content lost something (`merged-arrival`, `replaced`, a structural
  field that took the arrival's value, a repair), head's **whole file** is committed on the
  branch `horizon-conflicts` at `r<rev>/<path>`, next to `r<rev>/MERGE.txt` (the trailer
  lines plus, for structural merges, the list of entity uuids/fields that took the arrival's
  value). That branch is pushed with the backup, so the history is readable on GitHub.
* Never as a sibling file inside the project (`Foo.conflict.hasset`): a `.hasset` carries its
  UUID in META, a copy would put two assets on one UUID in the content manager.
* Outside the 5.3 repairs, the arrival's own content never loses (`delete-dropped` loses no
  content), so head's side is what gets preserved. When a repair fires, the repair can drop
  something from either side, so **both** pre-merge versions go to the branch
  (`r<rev>/<path>.head`, `r<rev>/<path>.arrival`).

## 6. Editor side

### 6.1 Opt-in

* `Config/ProjectSettings.json` gets a block (new `ProjectSourceControlSettings` in
  `src/HE_Core/include/Project/ProjectSettings.h`):
  `"sourceControl": { "mode": "git" | "teamServer", "team": "...", "project": "..." }`.
  Default `"git"` keeps `isDefault()` true for every existing project. The file is itself
  synced, so the whole team flips together.
* Server address and the member's login are **per user**, from topic 197's team settings
  (where the editor keeps the team server address and credentials): not in the project.
* A team admin creates the project on the server (CREATE_PROJECT) and uploads the initial
  tree as revision 1 (all entries `A`, no base). Others get it with MANIFEST + GET.
* With `mode = "teamServer"` the `SourceControlPanel` shows the team-sync view and hides the
  direct git actions. A `.git` that already exists stays untouched, but the editor no longer
  commits or pushes to it.

### 6.2 `TeamSyncService`

New class in `HE_SourceControl`, built like `GitService` (worker thread, `Command`/`Event`
queues, `pump()` on the main thread, `setOnStatusChanged`), so a save never waits on the
network. It uses topic 197's `HE_Net` team client for the ticket and opens the sync
connection itself (plain `TcpTransport` framing).

### 6.3 Local state and change detection

* `Saved/TeamSync/<team>-<project>.state`: `rev`, then per file `path \t sha256 \t size \t
  mtime`, i.e. the per-file base. `Saved/` is git-ignored and never uploaded.
* Scan: the project tree minus `RepoConfig::gitignoreText()` patterns, the project's own
  `.gitignore` and `.git/`. A changed size/mtime is rehashed (SHA-256, `Crypto/Sha256.h`).
* Upload trigger: after a successful save (`EditorApplication::saveSceneToPath`, after the
  `SceneDiskWatch::blocksSave` gate and the write; the asset tabs' saves; settings saves)
  plus a "Sync now" button. Debounced ~1 s so a "Save all" is one COMMIT. Each trigger
  uploads **everything** that differs from the state, so edits made in an IDE travel too.
* Flow: HAVE → PUT the missing → COMMIT → for each file whose result ≠ uploaded, and each file
  changed by others: GET, write via temp + rename, update the state. Then rev = reply rev.
* `sc-head` event from someone else: background pull. Files equal to their base are
  overwritten with head's; locally changed files are left alone and merged at the next save.
  Applied in `pump()`, not during Play.
* An open scene that changed on disk goes through the existing reload path
  (`SceneDiskWatch`): a clean world reloads, a dirty one gets the existing question.
* Conflict display: the team-sync view lists recent revisions with their trailers; a toast
  when one of *your* files lost something ("Scenes/Main.hescene: alex's later save won 2
  fields, your version is kept"), with "Open my version", which GETs the preserved blob.

## 7. GitHub backup

* **Credential:** the server generates an ed25519 key per project (`ssh-keygen -N ""`) on
  BACKUP_SET and returns the public key. The admin's editor registers it as a **deploy key
  with write access** on that one repo (`POST /repos/{owner}/{repo}/keys`, a new call next
  to `GitHubApi::createRepo`, using the token from the existing device-flow login, which
  never leaves the editor), or the admin pastes it in GitHub by hand. The server never
  holds a GitHub token, and the key only reaches that one repo.
* **Push:** worker job after each new revision, debounced (30 s quiet, at most 5 min
  behind under continuous saving), plus once on clean shutdown. `GIT_SSH_COMMAND="ssh -i
  backup_key -o IdentitiesOnly=yes -o UserKnownHostsFile=<known_hosts>"`, `git push <url>
  main:<branch> horizon-conflicts` (never `--force`), then `git lfs push --all <url>` when the
  revision added LFS objects.
* **Format on GitHub:** an ordinary repo whose `<branch>` (default `main`) is exactly the server's `main`: the
  project tree, one commit per save with the member as author and the trailers above;
  large media through LFS with `.gitattributes` entries; branch `horizon-conflicts`.
  Anyone can clone it and open the project with the direct git mode.
* **Failure:** a rejected non-fast-forward (someone pushed to that repo) stops the backup,
  state `diverged`, admin sees it in BACKUP_STATUS and a toast; the server never
  overwrites. Network errors retry with backoff. A first push into a branch that already
  exists on GitHub is refused the same way.
* **Existing repos:** the backup target is `url` + **branch** (BACKUP_SET gets a `branch str8`,
  default `main`; the conflicts branch is always `horizon-conflicts`). A team that already has its
  project on GitHub points the backup at that repo with a fresh branch such as
  `horizon-backup`, so the server never collides with the history pushed there directly.
* Disaster recovery (a new server from the GitHub backup via `clone --mirror`) is possible
  by construction but not part of this topic.

## 8. Security (open decision)

The team connection carries the password in plaintext (`TEAM_LOGIN`), and the sync connection
would carry the whole project. `SecureTransport` (X25519 + AES-256-GCM in `HE_Net`) protects
peer-to-peer sessions end to end, but the relay never sees inside those; here the server
**is** the endpoint and would have to terminate the encryption itself. Options: (a) a
SecureTransport-style handshake implemented in CollabSession with a pinned server key (no
deps, the most work); (b) TLS on the port, which needs a TLS library on the server and raw
TLS sockets in `HE_Net` (only `HttpsClient` exists); (c) accept plaintext for 0.7.0 and say
so in the UI. This blocks **deployment to 212.227.140.164** (step 5), not steps 2-4. Question
posted to topic 199 (#1326) for the queen; until answered, steps 2-4 build against plain TCP and keep the transport a seam.

## 10. Acceptance for step 5 (in protocol terms)

1. Two editors, same scene, different entities edited → both edits in head; outcome `merged`.
2. Both add a child to the same parent → both children present, `children` holds both.
3. Same component field changed by both → later save's value; earlier version on
   `horizon-conflicts`, both editors told (toast on the loser's side).
4. Same `.hmat` changed by both → later file wins, the other on `horizon-conflicts`.
5. Delete vs. change of one asset → asset still there, `delete-dropped`.
6. Every revision appears on the GitHub repo's `main` within the debounce window; a
   non-fast-forward on GitHub stops the backup with state `diverged` and is never forced.
7. A 60 MiB texture arrives as LFS on GitHub; a 120 MiB non-media file is refused with its name.
8. A project with `mode = "git"` behaves exactly as before (existing source-control tests).

## 12. As built in step 2 (2026-10-15)

Server code in CollabSession (`src/ScMerge`, `ScStore`, `ScGit`, `Process`, `Worker`, sync part of
`RelayServer`), protocol in its `src/Protocol.h` (top comment) and README section
"Quellcodeverwaltung (Team-Projekte)", which is the reference step 4 implements against.

**Numbers (final):** team op **20 `SC_TICKET`** (`project str8`; reply body 16 raw bytes), team
result **18 `no-such-project`**, team event kind **9 `sc-head`** (`project str8 | rev u64 |
member str8`, to every team connection of the team, the saver's own included), status **5
`sc-ready`**, **27 `no-project`** (28, 29 still reserved), frame types 10-13 as in 4.2.

**Differences from sections 4-5:**
* Creating a project: an admin gets a ticket and an `sc-ready` (text `no project yet`) for a
  project that does not exist; on that connection only `CREATE_PROJECT` works (others answer
  `no-project`). Non-admins get `no-such-project` already at the ticket.
* Results 0-9 as in 4.2, plus **10 no-project, 11 project-exists, 12 hash-mismatch** (PUT whose
  bytes do not match sha256/size). server-error text is generic; details go to the server log.
* Stream order (4.2 left it open): request first, then its SC_DATA (offsets from 0, last=1, an
  empty stream is one empty last frame); replies strictly in request order, a reply's SC_DATA
  before its SC_REPLY; pipelining allowed. A frame breaking this closes the connection.
* Reply bodies: MANIFEST `rev u64` (resolves 0 = head), GET `size u64`, COMMIT `rev u64 |
  changed u8`. A COMMIT that changes nothing (all `same`/`delete-dropped`) makes **no** revision.
  COMMIT outcome line: `outcome \t path \t sha256|- \t detail` (detail = the trailer tail, e.g.
  `against r4 by Alex (1 fields) lost=horizon-conflicts:r5/Scenes/Main.hescene`). A server-made
  change (LFS line in `.gitattributes`) comes as an extra line for `.gitattributes`.
* LOG stream: `R \t rev \t member \t unix-time \t subject` per revision, then `M \t <Horizon-Merge
  value>` per file; `count` capped at 1000.
* Scene repair (5.3): a dangling or cyclic `parent` goes to **the root** (the record with
  `parent: null`, head's), not to null: the loader maps every parentless record onto the one
  root (`SceneSerializer.cpp` `applySceneJson`, "#root-by-parent"), so null would merge an entity
  into the root. A cycle is cut at the entity whose merged parent is not head's (the arrival's
  edge). Entity records without `parent`/`children` keys keep them absent.
* An unknown per-file base (never stored) merges like add/add. Classes: `.gitignore` and
  `.gitattributes` are text; an unknown extension whose head content parses as a JSON object is json.
* `blobs.txt` (append-only, sha256 -> git oid / LFS pointer oid) is what GET of old or overruled
  content and MANIFEST of old revisions use; git oids are SHA-1, the protocol speaks SHA-256.
* LFS (step 2 writes it without the `git-lfs` binary): uploads >= 50 MiB live in
  `lfs/objects/`, media go into the tree as pointers with a `filter=lfs` line per path;
  non-media 50-100 MiB become plain blobs, >= 100 MiB `too-large`. Overruled LFS files sit on
  `horizon-conflicts` as pointers **without** `.gitattributes` lines on that branch (step 3).
* Limits: PUT <= 4 GiB, a HAVE/COMMIT stream <= 64 MiB, 64 queued requests per connection
  before reading pauses, 256 worker jobs before `busy`, 8 live tickets per member. No idle
  timeout on sync connections (TCP keepalive). Removing a member closes its sync connections and
  drops its tickets; a password change or token revocation does **not** (not in the design).

**Editor rules for step 4 that follow from this:** fetch (GET) every file whose outcome sha256
differs from what was uploaded; take `rev` from the COMMIT reply only when `changed = 1`, else
keep HEAD's; after `sc-head` from someone else, MANIFEST + GET; keep the per-file base = the
sha256 last received or accepted, never the local file's hash after an unsynced edit.

## 13. As built in step 3: GitHub backup (2026-10-15)

CollabSession `b6aaa00`: `src/ScBackup.{h,cpp}` (key, rules, push), scheduling in `RelayServer.cpp`
(`HandleBackupSet`, `BackupStatusBody`, `MarkBackupDirty`, `CheckBackups`, `StartBackupPush`,
`FlushBackups`), README section "GitHub-Backup" (the reference for step 4).

**Wire (final):** BACKUP_SET `url str16 | branch str8` (admins; **url empty = backup off**, branch
empty = `main`) → body `pubkey str16`. BACKUP_STATUS (any member) → `pushed_rev u64 | state u8 |
last_error str16 | time u64 | url str16 | branch str8 | pubkey str16` (the last three added to 4.2,
so the editor can show the target and re-show the key); `backup-not-set` (8) without a backup.
States: 1 pending, 2 ok, 3 failing (retried), 4 diverged (stopped). `time` = last push attempt.

**Differences from section 7:**
* State lives in `backup.txt` (not `project.txt`), written only by the backup worker.
* Pushes run on a **second worker thread**: a minutes-long LFS upload must not block saves. git's
  atomic refs/objects make the concurrent read safe; the backup never touches `ScStore`.
* Push = `git push --porcelain --atomic <url> <mainOid>:refs/heads/<branch>
  [<conflictsOid>:refs/heads/horizon-conflicts]` (explicit oids: `pushed_rev` is exactly what landed
  even if `main` moves meanwhile). LFS goes **first** (`git lfs push --all`, refs never point at
  missing content), via a `repo.git/lfs -> ../lfs` symlink (`-c lfs.storage=` would also redirect a
  local test remote's storage, so the probe "uploaded" nothing). git-lfs finds pointers by content,
  so overruled LFS files on `horizon-conflicts` go up without `.gitattributes` lines (verified locally).
* `non-fast-forward` / `fetch first` → diverged; any other refusal or error → failing, retry after
  delay×2ⁿ, capped at 10 min. A new BACKUP_SET resets it.
* Key: kept when only the branch changes, **new when the repository changes** (GitHub refuses one
  deploy key on two repositories). URLs: only github.com (git@, ssh://, https:// → git@ form); local
  paths only with `--sc-backup-allow-local` (tests), else an admin could push into any repo on the host.
* ssh: `-F /dev/null`, only the deploy key (`IdentitiesOnly`, `IdentityAgent=none`, `SSH_*` of the
  environment dropped), `BatchMode`, `StrictHostKeyChecking=yes` against github.com's three published
  host keys compiled in (fingerprints checked against docs.github.com on 2026-10-15), 20 s connect
  timeout. `Proc::Run` got a timeout (push 10 min) and a cancel flag; the child runs in its own process
  group so ssh under git dies with it.
* Schedule: dirty on each COMMIT that changed something; push after `--sc-backup-delay` (30 s) quiet,
  at most `--sc-backup-max-delay` (300 s) behind; immediately at start for every project with a
  backup; on stop one more push, waited for at most 30 s, then cancelled (runs again at next start).
