Multiplayer: one machine hosts and is the authority, the others join as clients and play in the host's world. The rows fall into five parts: the session (host, join, leave, status), the players, who owns an entity, replicated variables, and remote calls. Session events, onRep_<var> and the remote-call targets are script methods, listed under Callbacks. The examples below ran word for word in Lua and Python, host and client in both languages, over a real connection on one machine.

  • Hosting. host(port, name) answers true once the socket is open; the status is 1 at once and the host's scripts get onSessionStarted. Port 0 takes the project's Default port (Project Settings, Game, Multiplayer, 47824 in a new project). If that is 0 as well the system picks one, and no row reads it back, so a game that tells joiners its port hosts on a fixed one. Hosting again while a session runs ends it first (onSessionEnded, then onSessionStarted, a new session id and join code). It goes through leave(), so players who had joined are dropped; that part is read from the code, the re-host was measured with nobody connected.
  • Joining. joinDirect(address, port, code, name) answers true when the attempt has started (status 2); false for port 0 or above 65535, and for joinLan with no LAN entry at that index. The client's scripts get onConnected once the whole world has arrived (status 3), the host's get onPlayerJoined(player). A wrong join code never fails: the host refuses the handshake, but the client stays at status 2 with an empty lastError (measured for 8 seconds). Give up yourself, as the lobby example does.
  • LAN browsing needs the system's permission to use the local network. Without it (macOS asks per application) the host logs “the system refused to send an announcement” and every list stays empty; joinDirect keeps working. The LAN rows were not measured with the permission granted.
  • Player numbers. The host is player 1, joiners are 2, 3, … in join order, and a number is never reused. That is the number playerName, ping, kick, callClient, rpcSender and onPlayerJoined/onPlayerLeft use. It is not the connection number the anticheat rows take.
  • Ownership. Scene entities belong to nobody: ownerOf is 0. isLocallyControlled is true offline and for any entity without Replicates; for a replicated entity nobody owns it is true on the host and false on a client.

Replicated variables

  • Declare, then write on the host. declareVar…(entity, name, initial, notify) works on any entity and also offline; a declaration made before the session starts is carried into it (the health example declares in onStart). Only entities with Replicates on are sent to clients: on any other the variable exists on this machine only. Declaring a name a second time answers true and changes nothing (measured offline).
  • What a client sees. A write on the host reaches every client a moment later (well within half a second on one machine); with notify the client's script gets onRep_<name>(old), never the host's (it made the change) and never for a variable declared without notify. A client's own setVar… changes only its copy; the host sends its value again within a moment, even an unchanged one, and onRep_ fires once more with old = the client's value.
  • Types are not checked on write. A getter of another type answers zero (false, 0, "", 0,0,0). A setter of another type answers true and changes the variable's type, after which the declared getter reads zero; during a session the host then re-sends the entity's whole variable table every tick. Ints are 32-bit: 3000000000 is stored as −1294967296.
  • After the session ends, a client keeps the last values it received.

Known issue (build 7d49d44f): in Lua, old of a Vector variable is the number 0. The value handed to onRep_<name>(old) goes through a converter that has no case for vectors, so Lua always receives 0 (measured with old values 0,0,0 and 1,2,3). Python receives a list [x, y, z]. Read the new value with getVarVec3, and keep the previous one yourself if you need it. A Vector argument of a remote call from a HorizonCode graph goes through the same converter.

Remote calls

  • Who runs what. callServer on a client sends the call to the host, which runs the method of that name on the entity: its HorizonCode class first, else its Lua or Python script, else the C++ module (first one that has it). callClient and callAllClients go from the host to the clients' copies of the entity. The arguments after the name arrive with their types: integers, other numbers, booleans and strings as they are, a Lua table or Python list as a list, a Python dict as a table with __keys. Inside the method rpcSender() is the caller's player number (on a client: 1, the host).
  • Nothing runs locally in a script. Offline and on the host, callServer, callClient to the host's own player and the host's own share of callAllClients reach only a HorizonCode class. A Lua or Python method is not called and the row answers false, for callAllClients even though the clients were sent the call. On the host, call your own method directly (lever example).
  • Who may call. A client may call the entities it owns, plus functions opened with allowAnyClient (or Any Client on a HorizonCode function header). Anything else the host drops without a log line, while the client's callServer still answered true; with anti-cheat on it is a Hard report and the caller is removed at once (measured). allowAnyClient lasts for one session and answers false offline, so call it in onSessionStarted. It answers true on a client, where it changes nothing, and for an entity without a network id, which is refused with a log line.
  • A call needs a replicated entity: for any other the row answers false. The host accepts up to 60 calls per second from one client, averaged over 2 seconds; more are dropped (default, the Multiplayer page can change it).

Leaving and being removed

  • leave() ends the session on this machine, sends onSessionEnded and puts the status back to 0.
  • A client that is removed or loses the host gets onDisconnected(reason) and status 4, and no onSessionEnded. net.kick with anti-cheat off only closes the connection, so the client sees reason 1 and “Lost the connection to the host.”; with anti-cheat on the client is told first and sees reason 2 and “Removed from the session.”. The host's scripts get onPlayerLeft(player), by which time playerName of that player is already empty.
▲

Known issue (build 7d49d44f): a second session in the same scene replicates no scene entity. Hosting walks the scene for entities with Replicates on and skips those that already carry a network id; leave() does not clear it. After host → leave → host, or hosting twice, the log says “Session walk: 0 replicated scene entities”, and clients that join the new session get none of those entities: their variables and remote calls do not arrive.
