The host's anti-cheat scores what clients send and decides what to do about it. It runs on the host of a multiplayer session whose project has anti-cheat switched on (Project Settings, Game, Anti-Cheat). Each report reaches every script as onCheatDetected(reportId); the report… rows read it, respond overrules the host's reaction. A client gets the same callback once, when the host tells it that it is being removed.

▲

Known issue (build 7d49d44f): anti-cheat never runs, in the exported game and in Play as Host alike. The project setting does not reach the session: net.host, --host and Play as Host all open it without the anti-cheat settings. And the anti-cheat that scripts, graphs and C++ modules talk to is a second object that no session is connected to. So in every frontend isEnabled is false, check true, report, respond, kick and setPlayerLabel do nothing, the readers answer 0 or "", and onCheatDetected never fires. The rest of this section was measured with the anti-cheat connected by hand, the way the engine intends it.

  • player is a connection number, not a player number. Every row here that takes a player, and reportPlayer, counts the host's connections, which are numbered separately from the players of net. The first joiner was player 2 on connection 1; after a failed join attempt had used connection 1, the next joiner was player 2 on connection 2. No row converts one into the other, so take the number from reportPlayer. A report filed under net.rpcSender() (player 2) went to connection 2, which was nobody, and the real caller's score stayed 0. A connection nobody holds is scored and reported all the same.
  • Score and level. report(player, rule, weight, detail) adds weight to that connection's score, which halves every 30 seconds (the defaults on the Anti-Cheat page). Reaching 5 files a Suspect report (level 1), 20 a Confirmed one (level 2). Hard (level 3) is a single observation no honest build sends, for example a remote call to an entity the client may not call. reportDetail lists the observations behind the score (“Custom 6.00 (Aimbot: through wall)”).
  • Reactions. Unless a handler says otherwise the host logs Suspect and Confirmed reports and kicks on Hard. respond(reportId, response) replaces that, but only inside onCheatDetected, in the frame the report fired: respond(id, 1 + 8) made the host log and flag, 1 + 16 log and kick. A later call is ignored with the log line “no such pending report”. Log is always kept.
  • check always answers true. The rules on the Anti-Cheat page are saved with the project but nothing reads them yet (measured with a rule “Damage” from 0 to 100 and a value of 500), so code that applies a value only when check agrees keeps working when they arrive.
  • What the kicked client learns. Its scripts get onCheatDetected with reportPlayer 0 (“you”), then onDisconnected(2) with “Removed from the session.”. After kick(player, code) it reads reportReason = code, level 2 and an empty rule; after a kick by the host's policy or a respond, the rule's name and reason 0. Score and detail are never sent to a client. In the editor's Play mode nobody is kicked.
  • Labels. A client's join name is its label from the start; setPlayerLabel replaces it in the log and in later reports (“conn 1 [Anna#1]”). expectDisplacement was not measured here: it needs a moving character.
