Calling Conventions

Every function on this page comes from one table inside the engine, the API registry. A HorizonCode graph, a Lua script, a Python script and C++ game code all call the same row, so a function behaves the same in all four. What differs is how you spell the call and how arguments travel. These rules apply to every row below.

One function, four names

FrontendHow physics.addImpulse is called
HorizonCodethe node Add Impulse (search the node menu by that name)
Luahorizon.physics.addImpulse(self.entityId, 0, 5, 0)
Pythonhorizon.physics.addImpulse(self.entity_id, 0, 5, 0)

The C++ name listed with every row is the engine's own function behind it. A native GameLogic module does not link against the engine and cannot call it; it reaches a smaller set (save, entity lookup, physics, input, content, networking and anti-cheat) through the he:: service helpers, see Native C++.

Function names are camelCase in Python too: horizon.physics.addImpulse, not add_impulse. Four groups are not reachable as horizon.<group>.* from Lua and Python: transform, material, cursor and log. Scripts use the flat functions for them instead (horizon.setPosition, horizon.setMaterialParam, horizon.showCursor, horizon.log). Rows without a flat twin, such as transform.getWorldPosition, are HorizonCode and C++ only. Each group below says which case it is.

Arguments and results

Arguments are passed flat, in the order the signature lists them. A vector is spread into its numbers, it is not a table or a tuple:

Type in the signatureLuaPython
floatone numberone float (an int is accepted)
int, entity, ref, enumone integerone int
booltrue / falseTrue / False
stringone stringone str
vec22 numbers: x, y2 numbers
vec33 numbers: x, y, z3 numbers
color, vec44 numbers: r, g, b, a4 numbers
structone table with __typeone dict with "__type"

Results spread the same way. One value comes back as that value, several as Lua multiple return values or a Python tuple, none as nil / None. physics.raycast takes two vec3 and a float (seven numbers) and returns a bool, an entity, two vec3, a float and an int (ten values):

ground.lua 
local x, y, z = horizon.getPosition(self.entityId)
local hit, other, px, py, pz, nx, ny, nz, dist, layer =
    horizon.physics.raycast(x, y, z,  0, -1, 0,  50)
if hit then
    horizon.log("ground is " .. dist .. " below")
end
ground.py 
x, y, z = horizon.getPosition(self.entity_id)
hit, other, px, py, pz, nx, ny, nz, dist, layer = \
    horizon.physics.raycast(x, y, z,  0, -1, 0,  50)
if hit:
    horizon.log(f"ground is {dist} below")

Too few arguments is an error: Lua raises bad argument #n … (number expected, got no value), Python raises IndexError. The one exception is a missing bool in Lua, which silently reads as false. Extra arguments are ignored in both languages. Optional arguments exist only where a signature shows them in brackets, which is only on the flat functions.

Entity ids and “Self”

An entity is passed as its integer id: self.entityId in Lua, self.entity_id in Python, or whatever a lookup like horizon.entity.findByName returned. Invalid ids are tolerated: getters return a neutral default, setters do nothing.

▲

Always pass your own id. Parameters marked self in HorizonCode mean “the calling object” when a graph leaves the pin unconnected. A Lua or Python script is not such an object, so there it does not apply: 0 is passed on unchanged, the engine logs “Entity is empty and there is no calling object”, and the call acts on entity 0, the scene root. Write horizon.entity.getName(self.entityId), never horizon.entity.getName(0).

List results (not yet usable from scripts)

▲

A few rows return a list, such as physics.overlapSphere, physics.raycastAll, fs.list, save.list or scene.available, and process.run takes one. HorizonCode and C++ handle these fine. The Lua and Python bridge does not yet translate lists: such a call currently returns a single 0 or "" instead of the list. These rows are marked list: HorizonCode/C++ only below. Until the bridge is fixed, use them from a HorizonCode graph.

Events in the descriptions

The descriptions come from the editor and name HorizonCode events such as On Timer or On Http Response. A script receives only the events listed under Callbacks; those are linked where they appear. The others (On Http Response, On File Changed, On Menu Item, On Tray Item, On Row Bind, On Window Closed, On Dismissed, On Selection Changed, On Right Clicked) have no Lua or Python callback today. Where a query exists, poll it instead, for example horizon.http.done(ticket) each frame after horizon.http.get. Otherwise handle that part in a HorizonCode graph.

Actions and queries

Every row is either an action (it changes something: moves, spawns, plays, writes) or a query (it only reads and returns). In HorizonCode an action is a node with white execution pins that runs in sequence, a query is a data node without them. In a script both are ordinary calls, but the tag tells you whether a call is safe to repeat freely.

Project permissions

A few rows reach outside the game and only run when the project allows it, under Project Settings ▸ Permissions. Without the permission the call does nothing and returns its “failed” value (false, 0, an empty result), and the log says which permission is missing. The settings travel into the exported app, and they bind play mode in the editor the same way.

PermissionRows
Files outside the projectfs.* with an absolute path that the user did not pick in a file dialog, print.toPdf, db.open

Dialogs and the clipboard need no permission.

Remote calls take any arguments

horizon.net.callServer(entity, name, …), horizon.net.callClient(player, entity, name, …) and horizon.net.callAllClients(entity, name, …) accept any number of extra arguments after the function name and pass them on. Their types are taken from the values themselves: a boolean, an integer, any other number, a string, or a list/table of those. This is the one place where the registry signature (which has no slot for them) does not describe the script call. The receiving side is a method of that name on the target entity's script, see Callbacks.

Your own enums and structs

Project Types in Scripts

Enums and structs you create as assets in the Content Browser are available to scripts under horizon.enums and horizon.structs, built when the script runtime starts.

WhatLuaPython
Enum entry (an integer)horizon.enums.Weapon.Swordhorizon.enums.Weapon.Sword
New struct with its default valueshorizon.structs.Loadout() → tablehorizon.structs.Loadout() → dict

A struct value is a plain table / dict: one key per field plus __type, the path of the struct asset. Keep __type when you hand the value back, it is how the engine knows which struct it is. Missing fields keep their defaults, unknown keys are ignored. Inside a struct, fields are single values rather than spread: a vec2 is {x, y} / [x, y], a colour {r, g, b, a}, a transform {pos = {…}, rot = {…}, scl = {…}}, a list a sequence, and a nested struct a nested table. A map field is a Python dict (it keeps its order); in Lua it is a table plus a __keys list that holds the order. Structs go in and out of save.setStruct / save.getStruct this way.
